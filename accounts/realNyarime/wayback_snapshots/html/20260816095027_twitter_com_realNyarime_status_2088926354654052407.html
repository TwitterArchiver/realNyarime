界面虽然可以选择“超高”或“极致”思考强度，但实际发给模型服务的请求仍然是 reasoning_effort: high。这个问题目前已在 WorkBuddy Desktop 5.3.11、内置 CLI 2.115.0 上稳定复现，涉及 GPT、Kimi、Grok 等多个自定义模型，并非某一个模型服务的个例。包括Windows和Mac最新版v5.3.13也有相同问题。
复现方式比较简单：在 WorkBuddy 中配置一个支持 xhigh、max 的自定义模型，分别选择“高”“超高”“极致”发起对话，再通过本地 mock 服务捕获 WorkBuddy 实际发出的 Chat Completions 请求。捕获结果如下：
选择“高” → reasoning_effort: high
选择“超高” → reasoning_effort: high
选择“极致” → reasoning_effort: high
也就是说，界面上的三个不同档位最终被发送成了同一个 high。整个过程没有报错，也没有任何降级提示，用户从界面和对话记录中无法判断自己的选择没有真正生效。
进一步对照后发现，问题似乎不在第三方接口地址本身，而在自定义模型的能力识别链路。相同的外部测试地址下，使用未收录的自定义模型 ID 时，“极致”会降为 high；换成 WorkBuddy 内置能力目录中的模型 ID 后，xhigh 或 max 则可以得到保留。因此，是否降级主要取决于模型 ID 能否命中客户端内置能力目录，而不是该请求是否发往腾讯内部服务。
从当前请求处理链路初步定位，可能存在两步有损转换：首先，“极致”对应的 max 在进入底层 SDK 时被转换为 xhigh，导致 max 和 xhigh 过早合并；随后，自定义模型因为没有命中静态能力目录、无法取得 thinkingLevelMap，又被兼容规则从 xhigh 降为 high。最终形成：
max → xhigh → high
xhigh → high
自定义模型配置里的 reasoning.supportedEfforts 目前看起来只影响界面展示，没有进入实际请求的能力判定。即使在模型配置中补充 thinkingLevelMap，实际请求仍然会发送 high，因此暂时也没有可用的用户侧配置绕过方式。
这个问题的主要影响是：界面展示与实际请求不一致。用户以为自己正在使用“超高”或“极致”推理，实际上模型收到的只是 high。
